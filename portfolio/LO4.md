## 4. Evaluate limitations of the testing process, using statistical methods where appropriate

**4.1 Gaps and omissions.** *Bot strength* is untested: the tests show that bots act legally and that the three styles differ over 2,000 identical decisions, but nothing shows that a bot plays well, for example that the balanced style beats the passive one over many hands. No real person has played the game, so the qualitative requirements (clear prompts, a readable table) have had no *usability* or *acceptance* testing, and the bot-only tournaments stand in for real play. There is also *common-mode* risk: I wrote both the code and the tests, so a wrong assumption of mine can sit on both sides. The same holds for the *oracle*: the brute-force evaluator calls the same five-card function as the fast one, so five-card hands have no independent check.

**4.2 Targets and motivation.** Before measuring anything, the plan set *branch coverage* targets by risk: 95% for `card`, `deck`, `player`, `pot`, `betting` and `evaluator`, where a mistake gives the wrong winner or wrong chips; 90% for `probability`; 85% for `game`; 80% for `bot`, whose choices only need to be legal. Coverage is a proxy for adequacy: it shows where to look, not whether results are checked. Two further targets: the win-probability estimate within 2 percentage points of the exact value and 2,000 simulations in under 1 s; and, added for this section, a *reliability* target of no broken invariant in 1,000 seeded bot-only tournaments, which would put the 95% upper bound on the failure rate under 0.5%.

**4.3 Achieved against target.** `Card` (97%) meets 95%. `Deck` (92%), `betting` (92%) and `evaluator` (91%) are a few points under, and `game` (82%) is 3 under 85%. `Player` (78%) and `pot` (77%) are well under 95%; `bot` (56%) and `probability` (42%) are far from 80% and 90%. Most of that gap is unsatisfiable obligations: an older bot decision method and display-only hand tables are never called, so no test can run them. I report the extent reached, which counts them as missed. The accuracy and speed targets are met (0.22 s for 2,000 simulations). For reliability I ran 1,000 seeded tournaments (`tournament_stats.py`): 839,685 actions, each followed by an invariant check, and no failure. With zero failures in 1,000 runs, the exact 95% upper bound on the failure rate is 0.37%, so the target is met. 987 tournaments finished with one winner (98.7%, 95% interval 97.8% to 99.3%); 13 stopped at the 1,000-hand cap, which I put down to the fast mode's random win estimate. This is a simulated *operational profile* with bots, not people. The 17 injected faults (16 caught) support only a 71% to 100% interval for the suite's detection rate, and I found no real fault, so none of this estimates how many remain.

**4.4 Reaching the targets.** Delete the unused code and measure again; this alone should lift `bot` and `probability` most. Add property-based tests (Hypothesis) on the evaluator and pots, so thousands of random cases check properties such as "chips in equal chips out", far beyond the 140 hand-chosen ones. Add a second reviewer to reduce the common-mode risk, and run a usability session with three to five players, who would also show whether bot strength feels sensible.

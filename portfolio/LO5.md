## 5. Conduct reviews and inspections; design and implement automated testing processes

**5.1 Review.** I reviewed `evaluator.py` and `pot.py`, which decide winners and chip movement. Criteria came from the lecture checklist (meaningful names, bad data considered and tested, exceptions explicit, consistent types, formatting) plus cyclomatic complexity of at most 20 per function and no duplicated logic. The two evaluator functions score 26 and 25, the highest in the game, though neither nears 50. Issues: the oracle `evaluate_bruteforce` calls `evaluate_five`, so 5-card hands have no independent oracle; `Pot` keeps both an `amount` and per-player `contributions`, and `build_side_pots` patches over any difference, silently ignoring a shortfall; `evaluate_five` does not reject duplicate cards; `EvaluatedHand` cannot be hashed and lacks `<=`; `Pot.award` bypasses the `Player` API. The game never reaches the last three, and the invariant check watches the second. As a check on the review, 200,000 random hands gave identical results from the fast evaluator and the oracle, and 30,000 random pots lost no chips: no functional bug found. Nothing was fixed. I am the author and the only reviewer, so shared blind spots are likely.

**5.2 Pipeline.** A GitHub Actions workflow runs on every push and pull request, on Python 3.10 and 3.13: install `pytest` and `pytest-cov`; run all 140 tests with branch coverage, failing under a 70% total gate; run 20 seeded bot-only tournaments, which fail on any broken invariant. The gate is a safety net, not the targets: per-module targets from 4.2 are read from the coverage report. Mutation testing and a coverage trend are the next stages.

**5.3 Automation.** Every test is executable and follows arrange, act, assert, with expected values written into the test. Following the test pyramid, 117 of the 140 cases are unit and integration level, and a few system tests drive whole hands and seeded tournaments with no screen interaction: a patched `input` supplies the human's choices and a fixed deck stacks the cards. `run_checks.sh` runs the same two pipeline steps locally with one command.

**5.4 Demonstration.** Running `run_checks.sh` on 24 Nov: all 140 tests passed in 7.0 s with 75% total branch coverage (gate 70%), then all 20 seeded tournaments ran to a winner (28 to 403 hands each, no illegal bot action, no broken invariant).

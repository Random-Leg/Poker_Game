## 5. Conduct reviews and inspections; design and implement automated testing processes

**5.1 Review.** I reviewed `evaluator.py` and `pot.py`, because they decide who wins and how chips move. My criteria were the lecture checklist (meaningful names, bad data considered and tested, exceptions handled, consistent types, tidy formatting) plus two of my own: no duplicated logic, and no function with a cyclomatic complexity above 20. That measure counts the independent paths through a function, and 20 is the slides' threshold for "complex". The two hand-ranking functions score 26 and 25, the highest in the game and just over that line, but far below the slides' 50, so they stay testable. I found two weaknesses. First, the slow evaluator that checks the fast one calls the same five-card function, so five-card hands have no independent check. Second, `Pot` stores both each player's contribution and the total, and if the two ever disagreed, `build_side_pots` would hide it. As a check on the review, 200,000 random hands gave identical results from both evaluators and 30,000 random pots lost no chips, so I found no functional bug. I fixed nothing. As the author and only reviewer, I may share blind spots with the code.

**5.2 Pipeline.** The pipeline is a GitHub Actions workflow (`.github/workflows/tests.yml`) that starts by itself on every push and pull request, on a clean machine, using Python 3.10 and 3.13. It has three steps. It installs the test tools (`pytest`, `pytest-cov`). It runs all 140 tests while measuring branch coverage, and fails if total coverage falls below 70%. It then plays 20 seeded bot-only tournaments, which fail if any invariant breaks. The 70% gate is a safety net just under the current 75%, so a large drop is caught; the per-module targets from 4.2 are checked by reading the coverage report. The same steps run on my machine with `run_checks.sh`.

**5.3 Automation.** Every test is executable and follows arrange, act, assert, with expected values written into the test. Following the test pyramid, 117 of the 140 cases are unit and integration level, and a few system tests drive whole hands and seeded tournaments with no screen interaction: a patched `input` supplies the human's choices and a fixed deck stacks the cards. `run_checks.sh` runs the same two pipeline steps locally with one command.

**5.4 Demonstration.** Running `run_checks.sh` on 24 Nov: all 140 tests passed in 7.0 s with 75% total branch coverage (gate 70%), then all 20 seeded tournaments ran to a winner (28 to 403 hands each, no illegal bot action, no broken invariant).

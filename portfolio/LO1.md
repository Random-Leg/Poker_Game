## 1. Analyze requirements to determine appropriate testing strategies

**1.1 Range of requirements.** The game is specified by 60 one-sentence requirements in eight groups: deck, hand flow, betting, pots, hand evaluation, bots, probability estimate and robustness (`REQUIREMENTS.md`). 52 are functional *correctness* requirements, e.g. "a raise smaller than the last full raise is rejected unless it is all-in". Four are measurable: the win-probability estimate must run 2,000 simulations against eight opponents within 1 s (*performance*) and be within 2 percentage points of the exact value at 10,000 simulations; the same seed must reproduce the same game; and the three bot styles must differ in how often they bet. Each has a numeric threshold so that it is verifiable; "a reasonable time" would not be. Others cover *robustness* (invalid input never crashes or changes state) and information hiding (a bot is never given another player's cards). Four are qualitative (*maintainability*, clear output) and are checked by inspection.

**1.2 Level of requirements.** 32 requirements are unit level (the ace is low only in A-2-3-4-5), 19 integration (the engine gives each side pot to the best eligible hand) and 9 system (a bot-only tournament ends with one winner). Chip handling is required at all three levels as deliberate *redundancy*: pot equals contributions; no balance goes negative; the table holds 9,000 chips after every hand.

**1.3 Test approach.** Applying the *partition* principle, betting is tested with equivalence classes of legal and illegal actions and boundary values around the minimum and maximum raise; hand flow is a state machine, so it gets state-based tests. Hand evaluation has 134 million seven-card inputs, so beyond one example per category I compare the fast evaluator with a brute-force reference on random hands, using *diversity* as an oracle. The estimate is random, so it is tested statistically against exactly enumerated odds; the 2-point tolerance is four standard errors. Randomness is seeded (*restriction*) so a failing test fails every time (*sensitivity*). Details are in `docs/LO1_test_strategy.md`.

**1.4 Appropriateness.** Testing is *optimistically inaccurate*, so I recorded where it could accept faulty code. The reference evaluator shares its five-card routine with the fast one, so a fault there passes the comparison; five-card hands rely on hand-written cases instead. Exact odds can only be enumerated heads-up on the turn and river, so multi-opponent accuracy is unchecked. The timing test depends on the machine, which weakens sensitivity. Tests were written after the code, losing *timeliness*, so expected results are derived from the rules of poker, not from running the code. Not tested by choice: shuffle fairness (Python's library), security and load (local, single user) and validation with real users, so this is verification only.

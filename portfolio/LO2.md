## 2. Create a test plan and instrument code

**2.1 Test plan.** The plan covers all 57 requirements for ten modules and excludes shuffle fairness, security and load. It lists six risks with controls, for example: tests that copy the code instead of the rules (one person wrote both), so expected results are derived by hand from poker rules; and random failures, so every test is seeded. Modules are integrated *bottom-up*, critical ones (evaluator, pot, betting) first, since they decide who wins and how much. The hand is a *finite state machine* of seven states and 11 transitions, each tested. *Scaffolding* covers a stacked deck, a scripted player, a fixed win probability for bots and a bot-only tournament. Testing is complete when every requirement has a passing test and no critical or severe fault is open. Branch coverage must reach 80-95% per module. A mutation score of 80% for the critical modules was planned but deferred for lack of time.

**2.2 Evaluation of the plan.** Strengths: completion is decidable because every criterion is checkable, and the integration order isolates faults. Weaknesses: one person is developer and tester, a *conflict of roles*; deriving results from the rules reduces this but is not independent review. The code existed first, so only new code is test-first and *timeliness* is lost. Deferring mutation testing leaves how well the tests detect faults only partly measured, since coverage shows code run, not code checked. Testing found no fault in the game, which may mean sound code or shared assumptions between code and tests.

**2.3 Instrumentation.** Control already existed: a seed option and a bot decision that accepts a fixed win probability. I added two new files and changed no game module. `invariants.py` checks after every action that chips plus pot equal 9,000, no balance is negative, each player holds 0 or 2 cards, the board size fits the state, no card appears twice and the player to act can act. `simulate.py` plays seeded bot-only tournaments, records every action, counts illegal bot actions (the game hides them) and, on failure, reports the hand and last eight actions. This is justified because the chip, state and tournament requirements cannot be checked from outside the game. Nine corrupted states and an injected chip leak were all detected.

**2.4 Evaluation of the instrumentation.** 300 seeded tournaments raised no violation and no illegal bot action; the zeros mean something because the checks were shown to fire. Limits: checks run after actions, so a fault repaired within one action is invisible; they test consistency, not correctness, since a payout to the wrong winner still conserves chips; the game has no logging or timestamps; and the fast mode's random win probabilities left 3 of 300 tournaments unfinished. Improvements not made: logging in the game, timestamps, assertions in the game code and a record of each bot's strategy per decision.
